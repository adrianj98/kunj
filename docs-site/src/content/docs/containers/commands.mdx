All container actions live under `kunj container`, usually typed as `kunj ct`:

```bash
kunj ct <action> [branch] [arguments]
```

`[branch]` defaults to the branch you have checked out. If you are not on a branch (a detached
HEAD) and the terminal is interactive, kunj lets you pick from the repository's containers, or from
origin's branches when there are none. With no action at all, `kunj ct` lists the containers.

Every action accepts `--json` for machine-readable output; progress and warnings then go to stderr.
`--context <name>` runs that one command against another Docker context.

## start

Creates the branch's container, or resumes it if it already exists.

```bash
kunj ct start feature/search
```

A new container clones origin, so origin must have the branch with all of its commits. If the branch
is missing from origin or has unpushed commits, kunj asks whether to push it (in an interactive
terminal) and otherwise stops with `push it first (the container clones from origin)`.

| Flag | Use it to |
|---|---|
| `-c, --create` | Create a new branch inside the container from `origin/<base>`. Your local repository is not touched; the branch exists only in the container until it is pushed. |
| `--base <ref>` | Choose the base for `-c`. Defaults to `preferences.defaultBaseBranch`, else the repository's default branch. The base must exist on origin. |
| `--image <img>` | Use another image for this container, instead of `container.image`, the devcontainer or `kunj-sandbox`. A blueprint snapshot is never used with `--image`. |
| `--publish <ports>` | Publish container ports on `127.0.0.1`, e.g. `--publish 3000,5432`. See [Ports](#ports). |
| `--rebuild` | Rebuild the image and recreate the container on the same volumes. The workspace and home are kept. With Docker-in-Docker it rebuilds the `kunj-sandbox-dind` image but reuses the sandbox image under it. |
| `--no-snapshot` | Start without the blueprint's snapshot: clone origin and run the blueprint's tools and setup in the container. See [Blueprints](../blueprints/). |
| `--keep-on-error` | Keep what a failed start created, for debugging. A container whose firewall never came up is stopped, never left running. |
| `--keep-volumes` | With `--rebuild`: keep the volumes of services no longer declared (they are removed with them otherwise). |
| `--no-hooks` | Skip the `pre/post-container-create` hooks. |

```bash
# A new branch from develop, with the dev server's port published
kunj ct start -c feat/onboarding --base develop --publish 5173

# Pick up a new image (or new settings) without losing the workspace
kunj ct start feature/search --rebuild
```

Resuming a stopped container starts it behind a fresh network helper, runs the blueprint's
`maintain` commands and the devcontainer's `postStartCommand`, and leaves the clone as it was.
Resuming a container that is already running does nothing, unless its network helper was made by
an older kunj (one without what port forwarding needs): then `start` replaces the helper, swapping the
firewall rules in without a gap, and ends the port forwarders and MCP bridges that ran through the old
one (`kunj ct agent` starts them again). When the new helper's image cannot be built, the old helper is
kept; when the new helper fails, the container is stopped and `start` says so.

With [Docker inside](../configuration/#docker-inside-the-container) (`container.dockerInDocker`),
`start` first checks that the Docker host may run it and refuses, before creating anything, when it
may not: `sysbox` without the `sysbox-runc` runtime, `privileged` without
`container.allowPrivileged` or on Docker Desktop, and either with a devcontainer or a custom image.
The message says which setting to change. Once the firewall is up it starts `dockerd` in the
container (again on every resume) and prints `docker <mode>` in its summary. When the repository has
a compose file and Docker inside is off, `start` prints a one-line hint pointing at
[services](../services/).

## agent

Starts the agent in a `tmux` session named `agent`, or reattaches to it if it is already running.

```bash
kunj ct agent feature/search
```

The command is `container.agentCommand`, by default `claude --dangerously-skip-permissions`.
Anything after `--` is passed to it as extra arguments:

```bash
kunj ct agent feature/search -- --model opus "Fix the failing search tests and push"
```

Detach with `Ctrl-b d`. The agent keeps running inside the container until it exits or the
container stops. If the image has no `tmux`, kunj warns and runs the agent directly, in which case it
stops when you leave.

`agent` also starts a background [`kunj ct forward --auto`](#automatic-forwarding) for the container,
so a dev server the agent starts is reachable on your machine. It is not started when one is already
running for that container, or when `container.forward.auto` is `false`.
If the network helper is not running or has no `socat`, `agent` says so instead of starting a forwarder that
would fail. The background forwarder and bridge write their output to
`~/.kunj/logs/<container>-forward.log` and `<container>-mcp.log` (truncated past 1 MB), which is where to
look when a port is not forwarded.

With [`container.mcp`](../configuration/#a-browser-for-the-agent) set, `agent` also adds the bridged
servers to the container's Claude Code config and starts a background [`kunj ct mcp`](#mcp), so the
agent can drive a browser on your machine. Nothing happens without that setting.

### Several agents

`--session <id>` runs another agent next to the default one, in the tmux session `agent-<id>`
(the id is 1 to 32 letters, digits, `_` or `-`). `--kill` ends agents instead of starting one: with
`--session` that agent, without it the default agent and every `agent-<id>` one. It exits 0 whether
or not anything was running, also when the container is stopped.

```bash
kunj ct agent feature/search --session review -- "Review the diff on this branch"
kunj ct agent feature/search --session review --kill
kunj ct agent feature/search --kill            # every agent in the container
```

`kunj ct list --json` reports the container's agents in `agent.sessions`: `running` is true when
any runs and `state` is `waiting` when any waits for you.

## attach

Reattaches to the agent's `tmux` session (`--session <id>`: that agent's):

```bash
kunj ct attach feature/search
```

It fails with `No agent session` when the agent is not running; start it with `kunj ct agent`.

## open

Opens the container in your editor, attached over Docker. A stopped container is started first, the
same way `kunj ct start` resumes it, and so is a running one whose network helper or a service is down
(an out-of-date helper that is running is left to `kunj ct start`).

```bash
kunj ct open feature/search
kunj ct open feature/search --new-window
```

The editor is `worktree.editorCommand` (default `code`). VS Code and Cursor open `/workspace` in the
container through the Dev Containers extension, which must be installed. kunj writes the extension's
attached-container configuration for the container's image first, so the window opens as the
container's user in `/workspace`. Editors that cannot attach get the `docker exec` command to run
instead.

<Aside type="caution" title="Credentials">
While the window is attached, the Dev Containers extension copies your `~/.gitconfig` into the
container, installs a git credential helper that answers from your host's credentials, and forwards
your SSH agent and gpg-agent. The agent in the container can use all of them, for any host, not only
origin. Turn the git ones off in the editor's settings:

```json
"dev.containers.copyGitConfig": false,
"dev.containers.gitCredentialHelperConfigLocation": "none"
```

SSH and GPG agent forwarding have no setting: the extension forwards them whenever the editor runs
with `SSH_AUTH_SOCK` set or a gpg-agent running. kunj prints this warning on every `open`.
</Aside>

With `container.network.allow` set, the editor's server inside the container needs the VS Code
update and marketplace domains; kunj warns about it and you add them to the allowlist.

`--json` prints `{ success, branch, name, editor, uri, warning }`, `warning` being the credentials
warning above. For an editor that cannot attach it prints `{ success, branch, name, editor, uri: null,
exec }`, with the `docker exec` command in `exec`.

## shell

Opens an interactive login shell in `/workspace`, as the container's user. It uses zsh when the
image has it (the default image does), else bash, else sh.

```bash
kunj ct shell feature/search
```

```text
kunj ▸ feature/search /workspace ❯ git log --oneline -3
```

The shell's exit code becomes kunj's exit code.

### Keeping a shell running

With `--session <id>` the shell runs in a tmux session named `sh-<id>` inside the container, and
running the same command again reattaches to it, so the shell and whatever it runs survive closing
the terminal (the [workspace app](../../workspace-app/) uses this for its shell tabs). The id is
1 to 32 letters, digits, `_` or `-`. Without tmux in the image, or with `agent.tmux` set to `false`,
it is the plain shell; `agent.tmuxStatus` turns on tmux's status line.

```bash
kunj ct shell feature/search --session build     # start or reattach
kunj ct shell feature/search --session build --kill
```

`--kill` ends the session; without `--session` it ends every `sh-<id>` session in the container. It
exits 0 whether or not a session existed, and also when the container is stopped or gone; with
`--json` it prints `{ "killed": true }` or `{ "killed": false }`.

## exec

Runs one command in `/workspace` and exits with its exit code. Put the command after `--`:

```bash
kunj ct exec feature/search -- npm test
kunj ct exec feature/search -- git push
kunj ct exec -- git status -sb          # the current branch's container
```

The command is run directly, not through a shell. For pipes or `&&`, wrap it:

```bash
kunj ct exec feature/search -- sh -lc 'npm run build && npm run test:e2e'
```

Output streams to your terminal, and stdin is connected, so interactive tools work.

## file

Reads or writes one file of `/workspace` as the container's user, for tools that need a file without
a shell:

```bash
kunj ct file read feature/search src/app.ts          # prints the file
kunj ct file read src/app.ts                         # the current branch's container
echo 'new content' | kunj ct file write feature/search src/app.ts
```

`write` reads standard input to the end and creates missing directories. The path is relative to
`/workspace`; absolute paths and paths that leave it (`..`) are refused. With `--json`, `read` prints
`{ "path", "content" }` and `write` prints `{ "success": true, "path" }`; failures print
`{ "error": { "code", "message" } }` with the code `bad-path`, `not-found` or `write-failed`.

`file` is for text: `read` decodes the file as UTF-8. Symlinks inside `/workspace` are followed,
even when they point outside it; the sandbox boundary is the container, not the path check.

## forward

Forwards ports on your machine into the container, for as long as the command runs:

```bash
kunj ct forward feature/search 3000
kunj ct forward 8080:3000 5173          # current branch: host 8080 → container 3000, and 5173
```

```text
localhost:8080 → :3000
localhost:5173 → :5173
Forwarding; press Ctrl-C to stop
```

kunj listens on `127.0.0.1` only. A bare port uses the same port on your machine when it is free,
and another free port when it is not (the output says which). Each connection is tunnelled through
`docker exec … socat` in the container's network helper, which shares the container's network (so it
reaches servers that listen only on `localhost` inside the container) and is kunj's own code: nothing
is run in the branch container itself, and the image needs no tools for it. When the helper is not
running, `forward` refuses. Each new connection costs a moment to open: fine for
a browser and hot reload, not for load tests.

A sidecar [service](../services/)'s port is forwarded by naming the service:

```bash
kunj ct forward feature/search postgres:5432   # localhost:5432 → the postgres service
```

The tunnel goes through the service's own container, with `socat`, `bash` or `nc`, whichever its
image has; kunj refuses when it has none.

### Automatic forwarding

`--auto` forwards whatever the container listens on, as it appears:

```bash
kunj ct forward feature/search --auto            # until Ctrl-C
kunj ct forward feature/search --auto --detach   # in the background, until the container stops
```

```text
Forwarding the ports feature/search listens on; press Ctrl-C to stop
+ localhost:5173 → 5173
+ localhost:3001 → 3000
- localhost:3001 → 3000 (closed)
```

Every 2 seconds kunj lists the container's TCP listeners (one `docker exec` of
`cat /proc/net/tcp /proc/net/tcp6`, so any Linux image works). Each new one on port 1024 or above,
bound to all addresses or to `127.0.0.1`, is forwarded (a server listening only on IPv6 `::1` is
not, because the tunnel connects to `127.0.0.1`) to the same port on
`127.0.0.1` when it is free, else to the next free port; when the listener goes away the forward is
dropped. Ports in `container.forward.ignore`, and ports already published with `start -p`, are
skipped. The listing and the tunnels go through the network helper, as above. With `--json` each change is one line,
`{"event":"add","port":3000,"hostPort":3001}` (`"remove"` when it is dropped), and
`--auto --detach --json` prints `{"success":true,"branch":"feature/search","pid":48213}`.

Running forwarders and their ports, `kunj ct forward <port>` as well as `--auto`, are recorded in
`~/.kunj/container-forwards.json`; `kunj ct list` shows the ports (a service's with its `service`). A
forwarder belongs to one run of the container: a detached one exits on its own as soon as the
container stops or is started again (a restart gets a new network helper, and `agent` starts a new
forwarder). To stop one sooner, `kill` its pid.

### Ports

There are two ways to reach a server in the container:

| | `kunj ct forward` | `--publish`, `container.publish`, devcontainer `forwardPorts` |
|---|---|---|
| When | Any time, while the command runs | Fixed when the container is created |
| Server must listen on | `localhost` or `0.0.0.0` | `0.0.0.0` |
| Speed | One `docker exec` per connection | Native Docker port mapping |
| Change it | Run it again | `kunj ct start --rebuild` |

Published ports are bound to `127.0.0.1` on your machine, never to the LAN. If the port is taken,
kunj picks the next free one; `kunj ct start` and `kunj ct list` print the mapping.

## mcp

Bridges the MCP servers of [`container.mcp`](../configuration/#a-browser-for-the-agent) (for now only
the `chrome` browser server) into the container, in the foreground, for debugging. `kunj ct agent`
starts the same bridge in the background.

```bash
kunj ct mcp feature/search
```

The container cannot reach your machine, so the connection goes the other way: kunj keeps a
`docker exec` open into the container, as the container user, that listens on
`/run/kunj-mcp/chrome.sock` (mode 600; only creating the directory runs as root), and the container's
`~/.claude.json` gets an `mcpServers.chrome` entry that connects to it with `socat`. When Claude Code
connects, kunj starts the server's command on your machine (by default Chrome DevTools MCP 1.12.0
with a throwaway profile of its own) and pipes the two together. The server gets only `PATH`, `HOME` and the `env` you
configure, never the container's forwarded variables.

Every request from the container is checked before it reaches the server:

- only a fixed list of browser tools may be called (pages and navigation, clicks and typing, page
  snapshots and screenshots, console and network reads, `evaluate_script`, emulation), each with a
  fixed list of arguments; everything else, `upload_file` first of all, is refused, and `tools/list`
  only shows what is allowed;
- so no file path from the agent ever reaches the server (and an argument that looks like one,
  `filePath`, `sourcePath`, ..., is refused at any depth); the default browser refuses downloads, and
  its profile and temp files live in a directory that is deleted when the session ends;
- `navigate_page` and `new_page` may open only the host ports [forwarded](#automatic-forwarding) for the
  container, unless `allowOrigins` says otherwise;
- a request id must be a short string or a safe integer, and not one already in flight; a batch
  (a JSON array) gets a single error; a line that is not a JSON-RPC message is dropped; a line over
  4 MB from the container (16 MB from the server), or more than 8 MB of replies the container does
  not read, ends the session, and so does any error while handling a line.

The server's own `roots/list` request is answered by the bridge with no roots, and the container's
`roots` capability is removed from its `initialize`.

A refused request gets a JSON-RPC error. The initialize result tells the agent which host port each
forwarded container port is on.

One session at a time per server: when Claude Code disconnects or the server exits, both ends are
stopped and the bridge waits for the next session. The bridge belongs to one run of the container: it
exits when the container stops or is restarted.

Running bridges are recorded in `~/.kunj/container-bridges.json`. `kunj ct mcp` refuses to start a
second bridge for the same container; a background one exits on its own, or `kill` its pid.

## list

Lists the containers of the current repository. It is also what `kunj ct` does with no action.

```bash
kunj ct list
```

```text
Containers for shop:
──────────────────────────────────────────────────────────────────────
● feature/search  running  kunj-blueprint-shop:4d1f0a9c2b7e  [blueprint]  [agent]  +2 ahead
○ fix/cart-total  exited  kunj-sandbox:1.9.0-8c1d0e4b7a21
```

For each running container it shows whether the agent is running, how many commits the branch is
ahead of origin, whether the workspace has uncommitted changes, and its published and
automatically forwarded ports (`host→container`; in `--json`, `ports` entries with `kind` `"publish"`,
or `"forward"` with the forwarder's `pid`). `[blueprint stale]` means the
container was started from a snapshot that no longer matches the blueprint, and
`[firewall helper down]` means the network helper is not running (start the container again to bring
it back). `[dind sysbox]` or `[dind privileged]` marks a container with
[Docker inside](../configuration/#docker-inside-the-container); `--json` has `dind` (`"off"`,
`"sysbox"` or `"privileged"`) on every container. `[mcp chrome]` marks a container with a running
[MCP bridge](#mcp); `--json` has `bridges` (`[{ "name": "chrome", "pid": 48213 }]`) on every container.

| Flag | Use it to |
|---|---|
| `-a, --all` | List the containers of every repository. |
| `--no-status` | Skip the per-container check, for a faster listing. |

When a helper, service, volume or network is left over from a branch container that no longer
exists (one deleted with `docker rm`, say), the listing ends with an `orphans:` line, and `--json`
lists them in `orphans` (`[{ "kind": "volume", "name": "..." }]`). [`prune`](#prune) removes them.

## logs

Prints the output of the container, or of one of its [services](../services/):

```bash
kunj ct logs feature/search postgres
kunj ct logs feature/search postgres --follow   # keep streaming until Ctrl-C
```

With `--json` every line is printed as one JSON object, `{"service":"postgres","stream":"stderr","line":"..."}`
(`service` is `null` for the branch container, `stream` is `stdout` or `stderr`).

## stop

Stops the container, its network helper and its services. The workspace and home volumes are kept, so nothing is
lost; `kunj ct start` resumes it.

```bash
kunj ct stop feature/search
```

## remove

Deletes the container, its network helper, its services, its network and its volumes (the services'
volumes too).

```bash
kunj ct remove feature/search
```

Before deleting anything kunj checks the clone inside the container (starting it behind its firewall
first if it is stopped). It refuses when it finds any of:

- commits on any local branch, or a detached HEAD, that origin does not have;
- stashes;
- uncommitted changes to tracked files;
- an origin it cannot reach, since it then cannot tell what was pushed.

```text
✗ kunj-shop-feature-search-3fa2c1 holds work origin does not have:
  - unpushed commits on feature/search
  - 1 stash
Push it first, or use --force
```

Untracked files are not protected, as with `git worktree remove`.

| Flag | Use it to |
|---|---|
| `-f, --force` | Remove without checking for unpushed work. |
| `--keep-volumes` | Keep the workspace and home volumes. A later `kunj ct start` of the branch reuses them. |
| `--no-hooks` | Skip the `pre/post-container-delete` hooks. |

<Aside type="caution">
`--force` deletes the workspace volume, and with it everything in the container that was not pushed.
Use `--keep-volumes` if you are not sure.
</Aside>

## prune

Cleans up what branch containers leave behind in Docker:

```bash
kunj ct prune             # this repository: show the plan, ask once, remove
kunj ct prune --dry-run   # only show the plan
kunj ct prune --all       # every repository kunj has recorded (kunj repos)
```

It removes:

- **containers of branches deleted on origin** (a merged pull request, say), with their helper,
  services, network and volumes, as [`remove`](#remove) does. A branch counts as deleted only when
  origin no longer has it *and* the clone in the container has seen it there, so a branch made with
  `start -c` and never pushed is not touched. The same check for unpushed work runs first, and again
  just before removal: a container that holds commits, stashes or changes origin does not have is
  kept, and the plan says why. kunj asks origin once (`git ls-remote --heads origin`); when origin
  cannot be reached, no container is removed for this reason.
- **orphans**: helpers, services and networks labelled for a branch whose container no longer exists.
  A branch with anything created in the last 10 minutes is left alone (a start or `--rebuild` waits
  for its services before its container exists), and `list` does not call those orphans either.
  Volumes without a container (a workspace kept by `remove --keep-volumes`, or left by a `docker rm`)
  can hold unpushed work that no check can see, so they are listed as kept and removed only with
  `--force`.
- **snapshot build leftovers**: the temporary container of a [snapshot](../blueprints/) build that was
  killed (Ctrl-C, a crash, a reboot), when it has exited, was created but never started for over ten minutes, or has been alive for over a day (a paused one is a build committing its image), with its helper,
  services, volumes and network. There is no check for unpushed work: it holds none. In `--json` the
  entry has `reason: "snapshot-leftover"`.
- **old snapshot images**: [blueprint snapshots](../blueprints/) whose hash is not the current one.
  When the current hash cannot be worked out, every snapshot is kept.
- **old kunj images**: `kunj-sandbox`, `kunj-nethelper` and `kunj-sandbox-dind` tags of other kunj versions.
- **stopped containers older than `container.pruneAfterDays`** days, when you set it (off by
  default), after the same check for unpushed work.

An image a container still uses is never removed.

```text
Prune shop:
  remove kunj-shop-fix-cart-total-9b2e4f  branch fix/cart-total is gone from origin
  keep   kunj-shop-spike-cache-1c7d3a  branch spike/cache is gone from origin, but: unpushed commits on spike/cache
  remove volume kunj-shop-old-ui-5e8f20-ws  orphan: its branch container is gone
  remove image kunj-blueprint-shop:0a6c1d9e4b2f
  images: 812 MB
? Remove 3 objects? (y/N)
```

When stdout is not a terminal (a script, `| less`, the VS Code extension) or with `--json`, prune only
lists the plan unless you pass `--yes`; `--force` alone never removes anything without asking. Each
container removed runs the `pre/post-container-delete` hooks.

Planning, even a dry run, inspects each candidate container: a stopped one is started behind its
firewall for a moment and stopped again, as `remove` does. Only containers whose branch is missing
from origin or that are older than `container.pruneAfterDays` are inspected; with `--force` the old
ones are not.

| Flag | Use it to |
|---|---|
| `--dry-run` | Show the plan and remove nothing. |
| `-a, --all` | Prune every repository in `~/.kunj/repos.json` that is not hidden. |
| `-y, --yes` | Remove without asking, also from a script or with `--json`; the check for unpushed work still applies. |
| `-f, --force` | Skip the check for unpushed work and remove volumes without a container. Still asks, unless `--yes`. |
| `--no-hooks` | Skip the `pre/post-container-delete` hooks. |

<Aside type="caution">
`--force` removes containers of deleted branches even when they hold unpushed work, and volumes
whose container is gone. Run `kunj ct prune --dry-run --force` first to see what that would take.
</Aside>

## blueprint

`kunj ct blueprint init|snapshot|status|remove` manages the repository's
[blueprint](../blueprints/): how a new container installs its tools and dependencies, and the
snapshot image new containers start from.

## token

`kunj ct token status` says where a new container's GitHub token would come from: your environment
(`container.env`), `gh auth token` for origin's host, or nowhere. It never prints the token.

```bash
kunj ct token status --json
# { "github": { "source": "gh", "enabled": true } }
```

`source` is `env`, `gh` or `null`; `enabled` is `container.useGhToken`. See
[environment and secrets](../configuration/#environment-and-secrets).

`kunj ct token setup` gives containers a Claude Code token. It runs `claude setup-token` in your
terminal (you sign in in the browser), picks the token out of what it prints, checks that it works
and stores it as the global [secret](../../configuration/secrets/) `CLAUDE_CODE_OAUTH_TOKEN` for
containers. If the token cannot be found in the output you are asked to paste it. A token that does
not work is not stored. New containers get it; an existing one needs `kunj ct start <branch> --rebuild`.

`kunj ct token check` asks Claude Code once with the token new containers of this branch would get (a
stored secret, else `container.env`), as its only credential: other API keys are left out and a
throwaway Claude config directory is used, so your own Claude Code login cannot make a broken token
pass. It exits 1 when the token does not work.

```bash
kunj ct token check --json
# { "claude": { "source": "secret", "valid": true, "message": "The token works" } }
```

`valid` is `null` when there is no token or claude is not installed. Neither command prints the token.

## Getting work out

There is no "copy out" command, on purpose: origin is the only channel. The agent (or you, through
`kunj ct shell` or `exec`) commits and pushes; you fetch on your machine:

```bash
kunj ct exec feature/search -- git push
git fetch origin feature/search
```

The first `git push` of a new branch needs no `-u`: containers have `push.autoSetupRemote` turned
on. Opening a pull request from inside works too when the token allows it, since `gh` is in the
default image.
