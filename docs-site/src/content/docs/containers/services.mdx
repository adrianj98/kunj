A branch that needs a database gets its own. Each **service** runs in a container of its own, next
to the branch container on the branch's private network, and the branch container reaches it by
name: Postgres is `postgres:5432`. Another branch has its own network and cannot see it.

## Declaring services

In the [blueprint](../blueprints/) (`.kunj/blueprint.json`), or in the `container.services` setting
with the same shape:

```jsonc
{
  "services": {
    "postgres": {
      "image": "postgres:16-alpine",
      "env": { "POSTGRES_PASSWORD": "dev" },
      "port": 5432,
      "healthcheck": "pg_isready -h 127.0.0.1 -U postgres",
      "volumes": { "data": "/var/lib/postgresql/data" }
    },
    "redis": { "image": "redis:7", "port": 6379 },
    "worker": { "image": "ghcr.io/acme/worker:1", "command": ["run", "--dev"], "dependsOn": ["postgres", "redis"] }
  }
}
```

| Key | Meaning |
|---|---|
| `image` | Required. The image to run. |
| `env` | Its environment: only these variables, nothing from your shell or `container.env`. |
| `command` | Arguments that replace the image's command (an array of strings). |
| `port` | The port it listens on; shown by `kunj ct list`. |
| `healthcheck` | A command run with `sh -c` inside the service; the start waits until it succeeds. |
| `volumes` | `{ "name": "/path/in/container" }`. Named volumes only, one per branch; host paths are rejected. |
| `dependsOn` | Services started (and healthy) before this one. A cycle is an error. |

Names use `a-z`, `0-9` and `-`. When the same name is declared in several places the first wins:
the blueprint, then `container.services`, then the devcontainer's compose file.

## From a devcontainer compose file

When `.devcontainer/devcontainer.json` has a `dockerComposeFile`, kunj starts the services in it
except the devcontainer's own `service`. It reads the file with `docker compose config` and takes
`image`, `environment`, `command`, `healthcheck`, `depends_on`, named volumes and the first port of
`ports` or `expose`. It leaves out bind mounts, `build`, `privileged`, `cap_add`, `network_mode`,
`env_file`, `entrypoint`, `user`, `working_dir`, `tmpfs`, published ports and variables that would
come from your shell, and prints one warning listing them. A compose file with `include`, or with an
`extends` that names another file, is skipped with a warning: both make Docker read files from your
machine. kunj decides on the parsed file, so an explicit (`? include`), alias or escaped
(`"\x69nclude":`) key counts too, and a file that does not parse, has more than one document or uses a
YAML tag other than `!reset`/`!override` is skipped as well. `${VAR:-default}` becomes the default; nothing is read from your environment.

## Lifecycle

- **start** runs the services before the branch container, in `dependsOn` order, and waits for each
  health check (every 2 seconds, up to 2 minutes; after that it warns and carries on). They are up
  before `setup` or `postCreateCommand` runs.
- **Snapshots** start the services the same way, so a blueprint's `setup` can rely on them. Their
  data is never in the snapshot, and they are removed with the temporary container.
- **Migrations** against a service belong in the blueprint's `maintain`, written so they are safe to
  run again. A container started from a snapshot does not run `setup`: that ran during the snapshot
  build, against the build's temporary services, never the branch's own database. (A start without
  a snapshot runs `setup` instead of `maintain`, so a project that also starts without one lists the
  migration in both.)
- **stop** stops them; **start** on a stopped container starts them again, dependencies first.
  It also creates services declared since the container was made, and never removes one; a start
  that fails then stops the services it started.
- **start --rebuild** removes services no longer declared together with their volumes
  (`--keep-volumes` keeps the volumes).
- **remove** deletes them and their volumes (`--keep-volumes` keeps the volumes). The check for
  unpushed work is about the branch's clone only.
- A start that fails removes the services and volumes it created.

```bash
kunj ct list                               # each container's services and their state
kunj ct logs feature/search postgres       # a service's output; --follow keeps streaming
kunj ct forward feature/search postgres:5432   # localhost:5432 → the service
```

`kunj ct list --json` gives each container a `services` array of `{ name, state, port }`.

## What a service gets

The image of a service comes from the branch, so it is treated like the branch's own code:

- no variables from your shell or `container.env`, only its declared `env`;
- no bind mounts, only its named volumes;
- no added capabilities, no `--privileged`, no published ports.

<Aside>
Services are not behind the branch container's firewall: nothing of yours is in them, and only
containers on the same branch's network can reach them. They can reach the internet, for example to
download extensions.
</Aside>
