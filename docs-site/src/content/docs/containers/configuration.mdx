Container settings live under `container.*` in kunj's configuration. Like every setting they can
be global (`~/.kunj/config.json`) or per repository (`~/.kunj/<repo>/config.json`); see
[Configuration](../../configuration/overview/). A typical per-repository setup:

```json
{
  "container": {
    "env": ["ANTHROPIC_API_KEY", "GH_TOKEN", "NODE_ENV=development"],
    "files": ["~/.npmrc:~/.npmrc"],
    "publish": ["3000"],
    "memory": "6g",
    "cpus": "4"
  }
}
```

Most settings take effect when a container is **created**. To apply a change to an existing
container, recreate it on its volumes with `kunj ct start <branch> --rebuild`. The firewall settings
are the exception: they are read again every time a stopped container is started.

## Which image a container runs

kunj picks the first of:

1. `--image <img>` on `kunj ct start`;
2. the `container.image` setting;
3. the repository's `devcontainer.json`, read from origin at the branch's tip (see
   [below](#devcontainerjson));
4. kunj's own `kunj-sandbox` image.

When the repository has a [blueprint](../blueprints/), a new container starts from the blueprint's
snapshot instead, which is built on top of the image chosen above (never with `--image`).

An image chosen with `--image` or `container.image` runs as the image's own user, and its home
directory is not kept in a volume (kunj warns about this). The sandbox image and devcontainers with a
`remoteUser` get a home volume.

Whatever the image, it should have `git`, and `tmux` for `agent` to work fully. kunj warns when they
are missing. `forward` needs nothing in the image: it tunnels through the network helper.

## Environment and secrets

`container.env` lists what the container's environment gets. Each entry is either:

- a **name** (`GH_TOKEN`): the variable is copied from your environment when it is set there, and
  skipped when it is not;
- a **`NAME=value`** pair (`NODE_ENV=development`): passed as written, with
  [`${...}` variables](../../configuration/overview/) such as `${repoName}` or `${branch}` expanded.

The default forwards the model credentials and a GitHub token:

```json
["ANTHROPIC_API_KEY", "CLAUDE_CODE_OAUTH_TOKEN", "CLAUDE_CODE_USE_BEDROCK", "AWS_REGION", "GH_TOKEN"]
```

Setting `container.env` replaces this list, so keep the entries you still need. When
`CLAUDE_CODE_USE_BEDROCK` is on, the AWS keys and `AWS_PROFILE` are forwarded as well. Values
cannot contain newlines.

To clone a private repository, forward a token: `GH_TOKEN` (default), `GITHUB_TOKEN` or
`GITLAB_TOKEN`. kunj's git credential helper hands it to git, for origin's host only. `GITHUB_TOKEN`
and `GITLAB_TOKEN` are not in the default list, so add them if that is where your token lives:

```json
{ "container": { "env": ["ANTHROPIC_API_KEY", "GITLAB_TOKEN"] } }
```

Secrets reach the container only through the environment of `docker run`; see
[how secrets reach the container](../security/#how-secrets-reach-the-container).

## Files

Two kinds of host files can be copied into a new container. Both are copies, made once when the
container is created: later edits on either side do not sync.

**Keep files.** Files you keep out of git, such as `.env`, and have stored with
[`kunj worktree keep`](../../worktrees/keep-files/) are copied into `/workspace` at their usual
paths. Turn this off with `container.keepFiles: false`.

**`container.files`.** Any other file or directory, as `hostPath:containerPath`:

```json
{
  "container": {
    "files": [
      "~/.npmrc:~/.npmrc",
      "~/.zshrc:~/.zshrc",
      "${home}/.aws/config:~/.aws/config",
      "~/.claude/settings.json:~/.claude/settings.json"
    ]
  }
}
```

`~` and `${...}` variables are expanded on both sides; a container path that is not absolute (or
starts with `~`) is relative to the container user's home. A missing host file is skipped with a
warning.

<Aside type="caution">
Everything you copy in is readable by the agent. Don't copy credentials it does not need.

Don't copy your `~/.gitconfig`: it would replace the one kunj writes in the container, which holds
your git identity and the credential helper that lets git use the forwarded token.
</Aside>

## Ports

`--publish`, `container.publish` and a devcontainer's `forwardPorts` are all published when the
container is created, on `127.0.0.1` only. For ports you need now and then, use
[`kunj ct forward`](../commands/#forward) instead, which needs no rebuild and reaches servers bound to
`localhost`.

`kunj ct agent` also starts [`kunj ct forward --auto`](../commands/#automatic-forwarding) in the
background, which forwards every port of 1024 or above that the container starts listening on, on
`127.0.0.1` only. Set `container.forward.auto` to `false` to turn that off, or list ports it should
leave alone in `container.forward.ignore`:

```bash
kunj config --set container.forward.auto=false
kunj config --set container.forward.ignore=[9229,5555]
```

## Resources and Docker context

`container.cpus` and `container.memory` are passed to `docker run` as `--cpus` and `--memory`.
`container.dockerContext` makes every docker call use that context, for example to run containers in
Colima while Docker Desktop stays your default; `--context` overrides it for one command.

## Pruning old containers

[`kunj ct prune`](../commands/#prune) always removes the containers of branches deleted on origin. To
also remove containers that have been sitting stopped for a while, set `container.pruneAfterDays`
(off by default). A container's age counts from when it was created, and it still has to pass the
check for unpushed work:

```bash
kunj config --set container.pruneAfterDays=30
```

## Docker inside the container

By default there is no Docker inside a branch container: the host's Docker socket is never mounted.
For a repository whose development needs `docker build` or `docker compose up`, set
`container.dockerInDocker` and each branch container runs its own `dockerd`. Two branches running
the same compose file then never clash: they have separate daemons, so the same project names, ports
and volumes are fine. If all you need is a database or a broker, [services](../services/) are lighter
and need none of this; `kunj ct start` suggests them when the repository has a compose file and
Docker-in-Docker is off.

| `container.dockerInDocker` | What kunj does | Where it runs |
|---|---|---|
| `off` (default) | Nothing; capabilities are dropped as usual | Everywhere |
| `sysbox` | `docker run --runtime sysbox-runc` | A Linux Docker host with [sysbox](https://github.com/nestybox/sysbox) installed; refused when `docker info` does not list the `sysbox-runc` runtime |
| `privileged` | `docker run --privileged` | Only with `container.allowPrivileged: true`, and never on Docker Desktop (refused even then) |

Either mode:

- uses the `kunj-sandbox-dind` image, the sandbox plus Docker Engine, the docker CLI and the compose
  plugin from Docker's apt repository, built from the sandbox the first time (a new sandbox image
  rebuilds it). A devcontainer, `container.image` or `--image` is refused in this version;
- keeps `/var/lib/docker` on a per-branch volume, `<container>-docker`, so inner images survive
  `stop` and `--rebuild`; `remove` and `prune` delete it with the other volumes. `--rebuild`
  rebuilds the `kunj-sandbox-dind` image and the container, but reuses the sandbox image it is built
  on when that exists (remove the `kunj-sandbox` image to rebuild it too);
- keeps the container's capabilities, which `dockerd` needs, and sets `KUNJ_DIND=<mode>` in its
  environment;
- starts `dockerd` as root once the firewall is up, on every start, before the blueprint's `setup`
  and `maintain`. When it does not answer within 30 seconds, the start warns and carries on; its log
  is `/var/log/kunj-dockerd.log` in the container. The sandbox user reaches it through the `docker`
  group, so `docker` works in `kunj ct shell` and for the agent;
- adds Docker Hub (`registry-1.docker.io`, `auth.docker.io`, `index.docker.io`,
  `production.cloudflare.docker.com`), `ghcr.io` and `pkg-containers.githubusercontent.com` to the
  [allowlist](../security/#allowlist-mode) when you use one.

A [blueprint snapshot](../blueprints/) is built on the `kunj-sandbox-dind` image but never runs
`dockerd`, so no inner images end up in it. `kunj ct list` tags these containers `[dind sysbox]` or
`[dind privileged]`; `--json` has `dind` on every container. The mode is fixed when a container is
created: after changing the setting, `kunj ct start <branch> --rebuild` applies it. A container
created `privileged` is not started again once `container.allowPrivileged` is no longer true, and
one created with `sysbox` is not started when the daemon has lost the runtime; set it back, or
`kunj ct remove` (or `--rebuild`) it.

Read [what Docker inside costs](../security/#docker-inside-the-container) before turning it on.

### A dedicated VM for privileged mode

On a Mac, `privileged` lets the agent become root on the Docker VM. Docker Desktop's VM shares your
home directory, which is why kunj refuses it there. OrbStack and a default Colima VM share your home
directory with the VM in the same way; kunj only recognises Docker Desktop, so it does not refuse
them, but `privileged` does not belong there either. Give it a VM (or Colima profile) of its own with
no shared mounts, for example a Colima profile that mounts only an empty directory instead of your
home:

```bash
mkdir -p ~/.colima-dind-empty
colima start dind --mount ~/.colima-dind-empty   # replaces the default $HOME mount
colima ssh -p dind -- ls -R /Users             # check: only the empty directory
kunj config --set container.dockerContext=colima-dind
kunj config --set container.dockerInDocker=privileged
kunj config --set container.allowPrivileged=true
```

These go in the repository's configuration (the default for `kunj config --set`), so only the
repository that needs Docker inside runs in that VM.

## devcontainer.json

When neither `--image` nor `container.image` is set, kunj looks for `.devcontainer/devcontainer.json`
or `.devcontainer.json` on origin, at the tip of the branch being started (or the base, with `-c`).
Comments and trailing commas are allowed. kunj supports this part of the spec:

| Key | What kunj does with it |
|---|---|
| `image` | Runs that image. |
| `build.dockerfile`, `build.context`, `build.args` | Builds the image from the branch's files, tagged `kunj-<repo>:<hash>`; rebuilt when the Dockerfile, its context or the arguments change. Paths must stay inside the repository. |
| `remoteUser` | Runs as that user, with a home volume at `/home/<user>`. Must not be `root`. |
| `containerEnv` | Added to the environment. It cannot override forwarded secrets or `KUNJ_*`. |
| `forwardPorts` | Published on `127.0.0.1` like `--publish`. |
| `postCreateCommand` | Runs once per container, in `/workspace`, as the user. If it fails it runs again on the next start. |
| `postStartCommand` | Runs on every start of the container. |
| `dockerComposeFile`, `service` | The compose file's other services run as [services](../services/) next to the container; `service` (the devcontainer itself) is skipped. |

Anything else (features, `onCreateCommand`, `customizations`, mounts, `runArgs`, ...) is ignored
with a warning naming the keys.

```jsonc
// .devcontainer/devcontainer.json
{
  "build": { "dockerfile": "Dockerfile", "args": { "NODE_VERSION": "22" } },
  "remoteUser": "node",
  "containerEnv": { "DATABASE_URL": "postgres://localhost:5432/dev" },
  "forwardPorts": [3000],
  "postCreateCommand": "npm ci",
  "postStartCommand": "npm run db:migrate"
}
```

<Aside>
The devcontainer is read from the branch, which the agent can change and push. kunj refuses a root
user, replaces the image's entrypoint so nothing in it runs before the firewall, and warns before it
builds a Dockerfile the branch has changed, since image builds have full network access. See
[Security](../security/#capabilities-and-users).
</Aside>

## The sandbox image

Without a devcontainer, containers run `kunj-sandbox`, which kunj builds locally the first time you
need it (tagged `kunj-sandbox:<kunj version>-<hash>`, so a new kunj version rebuilds it). It is
Debian bookworm-slim with:

- `git`, `git-lfs`, `curl`, `tmux`, `socat`, `zsh`, `openssh-client`, `gnupg`, `procps`, `iproute2`;
- Node.js 22, the GitHub CLI `gh`, and Claude Code;
- a user `dev` (uid 1000) with zsh as its shell, and no `sudo`.

Global npm packages install into `~/.npm-global`, inside the home volume, so the agent can add tools
without root and they survive restarts. For tools every container of a repository needs, use a
[blueprint](../blueprints/) instead.

### Shell defaults

The image's `/etc/zsh/zshrc` sets up a usable shell without a dotfile:

- a prompt that shows the branch: `kunj ▸ feature/search /workspace ❯`, with `sandbox` on the right
  and a red arrow after a failed command;
- 50,000 lines of shared history in `~/.zsh_history`, kept in the home volume;
- completion with a menu, `autocd`, emacs key bindings;
- aliases `ll`, `gs` (`git status -sb`) and `gl` (`git log --oneline -20`);
- new shells start in `/workspace`;
- environment written by blueprint presets (such as `JAVA_HOME`) is loaded.

To use your own configuration, copy your `~/.zshrc` in with `container.files`. It is read after the
defaults, so it wins.

### Environment inside the container

kunj sets these in every container, whatever the image:

| Variable | Value |
|---|---|
| `KUNJ_CONTAINER` | `1`, so scripts can tell they run in a kunj container |
| `KUNJ_BRANCH` | The branch the container was started for |
| `KUNJ_REPO` | The repository's name |
| `KUNJ_CREDENTIAL_HOST` | Origin's host (and port), the only host the credential helper answers for |

`shell`, `exec` and `agent` also pass your terminal's `TERM` (and `COLORTERM`) and a UTF-8 locale,
so full-screen tools render as they do on your machine.

## Hooks

kunj runs hooks around creating and removing containers. Install them as scripts or commands as
described in [Hooks](../../configuration/hooks/).

<HookTable filter="container" />

- The create hooks run only when `kunj ct start` creates a container (including `--rebuild`), not
  when it resumes one. `pre-container-create` runs before the image is chosen, so its `image` is
  empty.
- A failing `pre-container-create` or `pre-container-delete` hook aborts the command before anything
  is created or deleted.
- `--no-hooks` on `start` or `remove` skips them.

Hooks run on your machine, not in the container. For example, to note each new container in a log:

```json
{
  "hooks": {
    "post-container-create": "echo \"$(date) ${container} ${image}\" >> ~/.kunj/containers.log"
  }
}
```
