<Aside type="caution" title="Preview">
Cloud machines work end to end on Google Cloud, but are new: `kunj ct list`, `kunj events` and the apps
do not show machines yet (use `kunj machine list`), and a first start on a new machine takes several
minutes because it installs Docker and builds the images there. Design and status:
[cloud-machines.md](https://github.com/adrianj98/kunj/blob/main/docs/specs/cloud-machines.md).
</Aside>

A cloud machine is a small VM (8 GB by default) that runs Docker and `kunj serve` for one branch.
Nothing on it but that branch's containers, its own kernel, no public address. When the branch's agent
goes quiet the machine sleeps and costs only its disk; the next command wakes it in seconds.

kunj never asks you to run cloud commands. A **coordinator** does: an ordinary `kunj serve --machines`
that alone talks to the cloud and to the machines. It runs in one of two places:

- **On your laptop.** Set `machine.provider` and kunj starts a coordinator on its own, on loopback,
  the first time a `kunj machine` command needs one. It uses your own `gcloud` login and exits after an
  hour without a request. Nothing to install or keep running.
- **On a tiny always-on VM**, when more than one person or laptop shares the machines. Every client
  connects to it with a token of its own and needs no cloud login at all.

## Set up Google Cloud

<Steps>

1. **Install and log in to `gcloud`** on the machine that will run the coordinator (your laptop, to
   start with):

   ```bash
   gcloud auth login
   ```

2. **Prepare the project once.** Machines get no external IP, so the network needs a Cloud NAT for
   their outbound traffic, and a firewall rule that lets Identity-Aware Proxy reach `kunj serve` on
   machines tagged `kunj-machine`:

   ```bash
   gcloud compute firewall-rules create kunj-serve-from-iap --network default \
     --allow tcp:7433 --source-ranges 35.235.240.0/20 --target-tags kunj-machine
   ```

   Your account needs `roles/iap.tunnelResourceAccessor` and permission to create instances.

3. **Tell kunj which project and zone:**

   ```bash
   kunj config --set machine.provider=gce --global
   kunj config --set-json 'machine.gce={"project":"my-project","zone":"us-central1-a"}' --global
   ```

4. **Check it:**

   ```bash
   kunj machine providers
   ```

   This starts the local coordinator and prints the sizes it will use.

</Steps>

## What a new machine installs

`kunj machine create` boots Google's stock Ubuntu with a startup script from kunj: it installs Docker,
Node and kunj, then starts `kunj serve` so the coordinator can pair with it. From a bare image that takes
a few minutes; the log is `/var/log/kunj-bootstrap.log` on the machine. `machine.kunjPackage` picks the
kunj it installs (`kunj@1.4.0`, or `github:owner/repo#ref` to build a branch), and `machine.image` names
an image of your own that already has everything, which starts in seconds.

## Removing

`kunj ct remove <branch>` checks the container for unpushed work, removes it, and then deletes the
branch's machine and its disk. With `--keep-volumes` the machine is kept, because the volumes are on its
disk; `kunj machine delete <branch>` removes it later.

## Bake an image so new machines start fast

```bash
kunj machine image build
```

This makes a temporary builder machine, installs everything on it, builds your blueprint's snapshot
there, saves its disk as a machine image and deletes the builder. Every new machine of the repository
then boots from the newest image, so nothing is installed or built again. Bake a new one after you
change the blueprint. `kunj machine image` lists the images and `kunj machine image delete <name>`
removes one; a new bake deletes the older ones itself. `--no-snapshot` bakes an image without the
blueprint snapshot.

## Share caches between machines

A machine runs one branch, so a [cache](../configuration/#a-cache-shared-by-every-branch) on it starts
as a copy of what the machine image held. A cache store keeps the caches in a bucket, so a change
made on one machine reaches the next ones without a new image.

Create a bucket and a service account that can only use that bucket:

```bash
gcloud iam service-accounts create kunj-machine --project my-project
gcloud storage buckets create gs://my-kunj-cache --project my-project --location us-central1 --uniform-bucket-level-access
gcloud storage buckets add-iam-policy-binding gs://my-kunj-cache --member serviceAccount:kunj-machine@my-project.iam.gserviceaccount.com --role roles/storage.objectAdmin
```

Tell the coordinator about both. Each coordinator has its own setting, so set it where that
coordinator runs (here, for the one on your computer):

```bash
kunj config --set-json 'machine.gce={"project":"my-project","zone":"us-central1-a","serviceAccount":"kunj-machine@my-project.iam.gserviceaccount.com"}' --global
kunj config --set-json 'machine.cache={"bucket":"my-kunj-cache"}' --global
kunj machine coordinator stop
```

From then on:

- A new branch container first pulls every cache from the bucket, before your blueprint's `setup` and
  `maintain` run. Only files that differ are downloaded.
- `kunj ct cache push` copies the branch's caches to the bucket. Nothing is pushed on its own, so the
  bucket only changes when you say so.
- `kunj ct cache pull` makes the machine's caches equal to the bucket again.
- `kunj ct cache status` shows the caches and where they are stored.

```bash
kunj ct cache push
```

A push makes the bucket equal to that machine's cache, and a pull makes the machine's cache equal to
the bucket, including deletions. File contents, dates, symlinks and the executable bit are kept. Other
permissions are not. An empty cache is not pushed unless you add `--force`, so a new machine cannot
empty the bucket by mistake. Machines created before the service account was set cannot reach the bucket.
Remove and start them again.

The branch container itself cannot reach the bucket. The copy runs in a separate short-lived container
on the machine.

## Run a branch on its machine

Name the coordinator with `--remote`: `machines` is the one kunj starts on this machine.

```bash
kunj ct start feature/search --remote machines   # makes or wakes the machine, then the container
kunj ct agent feature/search --remote machines
kunj ct shell feature/search --remote machines
kunj ct exec feature/search --remote machines -- npm test
```

`start` creates the branch's machine when there is none (`--size large` for a bigger one). Commands
that act wake a sleeping machine, which takes about 20 seconds; `stop` and listings never do. To make
it the default for a repository:

```bash
kunj config --set container.remote=machines
```

A machine goes to sleep by itself after `machine.idleMinutes` (30) with no command, no open terminal
and no agent working. Its memory is kept, so the container, its tmux sessions and a waiting agent are
there when it wakes.

## On AWS

kunj can run the machines on Amazon EC2 instead. Set the provider and its settings where the
coordinator runs:

```bash
kunj config --set machine.provider=ec2 --global
kunj config --set-json 'machine.ec2={"region":"us-east-1","subnet":"subnet-0abc1234","securityGroups":["sg-0abc1234"]}' --global
```

The subnet must be private with a NAT gateway. To reach machines from your computer, install the
AWS Session Manager plugin and add `"instanceProfile"` with a role that allows Session Manager. Sleep
uses EC2 hibernation. The cache store is an S3 bucket.

:::caution
The AWS provider passes kunj's provider tests against a simulated `aws` command. It has not been run
on a real AWS account yet.
:::

## Machines sleep on their own

A machine goes to sleep after 30 minutes with no agent working and no terminal open
(`machine.idleMinutes`). The coordinator does this while it runs. If your computer is closed, the
machine does it itself 15 minutes later. For that, its service account needs permission to suspend
instances:

```bash
gcloud iam roles create kunjSelfSuspend --project my-project --permissions compute.instances.suspend,compute.instances.get
gcloud projects add-iam-policy-binding my-project --member serviceAccount:kunj-machine@my-project.iam.gserviceaccount.com --role projects/my-project/roles/kunjSelfSuspend
```

## Stop for the day

`kunj ct stop` stops the container and puts its machine to sleep. You pay only for its disk while it
sleeps, and `kunj ct start` wakes it with everything as it was. Add `--keep-awake` to stop only the
container.

```bash
kunj ct stop
```

## See your machines

`kunj ct list` shows containers on running machines, and one row for each machine that is asleep.
Listing never wakes a machine.

```bash
kunj ct list
```

To run your own script when a machine is made or deleted, use the hooks `pre-machine-create`,
`post-machine-create`, `pre-machine-delete` and `post-machine-delete`. They run on your computer and
get the branch, the machine name and the provider.

## Clean up old machines

`kunj machine prune` finds machines you no longer need: ones whose branch was deleted on origin, and
ones left running with no container. It shows the list first and asks before deleting.

```bash
kunj machine prune
```

A machine that holds work origin does not have is kept. A sleeping machine is kept too, because kunj
does not wake a machine just to look inside it. Add `--force` to delete those as well.

## Commands

```bash
kunj machine create feature/search   # make the branch's machine and wait until it answers
kunj machine                         # this repository's machines, any state
kunj machine suspend feature/search  # sleep now (memory kept, no compute charge)
kunj machine resume feature/search
kunj machine delete feature/search   # the machine and its disks; the branch is on origin
kunj machine coordinator             # the local coordinator: pid, port, log
```

Without a branch, a command uses the current one. Every command takes `--json`; errors carry a code
such as `machine-not-found`, `provider-cli-missing` (gcloud missing or not logged in) or
`machine-token`.

## Sizes and cost

| `machine.size` | Google Cloud shape | Memory | About, per hour running |
| --- | --- | --- | --- |
| `small` | e2-medium | 4 GB | $0.034 |
| `medium` (default) | e2-standard-2 | 8 GB | $0.067 |
| `large` | e2-standard-4 | 16 GB | $0.134 |

Any provider shape also works (`--size n2d-highmem-8`). A sleeping machine costs only its disk, about
$3 a month for the default 30 GB, so delete the machines of merged branches.

## A shared coordinator

When a second laptop should see the same machines, run the coordinator on a small VM in the same
network (an e2-micro is enough) with the same `machine.*` settings, and give each client a token:

```bash
kunj serve --machines --listen <internal-ip>:7433 --allow-remote-listen
kunj serve token add laptop-b --machines
```

Set `machine.network` to `private` there, so it reaches machines on their internal address. On each
laptop, add it like any remote and name it on the command:

```bash
kunj remote add cloud --url http://127.0.0.1:7433 --token-stdin   # through an IAP tunnel or a tailnet
kunj machine --remote cloud
```

`kunj ct … --remote cloud` then runs a branch on its machine through that coordinator.

`kunj serve token list --machines` shows the clients, never their tokens; `token remove` revokes one.
