Tokens such as `GH_TOKEN` or `CLAUDE_CODE_OAUTH_TOKEN`, and app secrets such as `DATABASE_URL`, usually
live in shell exports and plaintext `.env` files. `kunj secret` keeps them in one encrypted store in
`~/.kunj` instead, and kunj hands each secret only to the places it names: commands you run on your
machine, new worktrees, and [branch containers](../../containers/overview/). A desktop app started
from Finder gets them too, because kunj opens the store itself rather than relying on your shell.

```bash
kunj secret set GH_TOKEN --global            # asks for the value, never takes it as an argument
kunj secret import .env --delete             # move a plaintext .env into the store
kunj secret list
kunj run -- npm run dev                      # the command gets the secrets in its environment
```

## Scopes

Each secret belongs to one scope:

- **global** (`--global`), in `~/.kunj/secrets.enc`: for every repository. Global secrets are only
  ever environment variables.
- **repo** (the default), in `~/.kunj/<repo>/secrets.enc`: for every branch of this repository.
- **branch** (`--branch <name>`, or `--branch` alone for the current one), in the same file as the
  repo's: for one branch only.

Repo and branch secrets need a repository: outside one, only `--global` works.

When kunj resolves the secrets for a branch it takes global, then repo, then branch, and the most
specific wins. So a `DATABASE_URL` set with `--branch feature/x` replaces the repo's `DATABASE_URL`
on that branch, and every other branch still gets the repo value.

## Targets and delivery

Every secret says where it may go (`--targets`):

- `host`: commands kunj runs on your machine (`kunj run`, `kunj agent`, `kunj worktree shell`) and
  files written into your worktrees.
- `container`: branch containers. Nothing reaches a container unless its secret says `container`.

The default is both. It also says how it is delivered:

- as an **environment variable** (the default; `--no-env` turns it off), and/or
- as a line in a **file** (`--file .env`), relative to the worktree root. Several secrets can share
  one file; kunj writes `NAME="value"` lines sorted by name.

```bash
kunj secret set STRIPE_KEY --targets host --file .env
echo "$TOKEN" | kunj secret set NPM_TOKEN --branch release/2.0   # piped values work too
```

`set` reads the value from a hidden prompt, or from stdin when it is piped. It never takes it as an
argument, which would show up in `ps` and your shell history.

## Importing a .env

```bash
kunj secret import .env
```

```text
Import into repo:
  DATABASE_URL  add
  STRIPE_KEY    add
? Import 2 secret(s)? Yes
✓ Imported 2 secret(s) into repo: DATABASE_URL, STRIPE_KEY
```

Imported secrets go to repo scope, for host and container, as environment variables and back into
`.env`, so new worktrees still get their `.env`. kunj shows the names it will add or replace (never
the values) and asks once; `--yes` skips the question. `--delete` removes the source file afterwards,
and its [keep file](../../worktrees/keep-files/) copy too, so the plaintext version is gone.

The file is read as dotenv: `KEY=value`, `export KEY=value`, single and double quotes, comments, and
values over several lines in quotes. `${OTHER}` is stored as written, not expanded. A line kunj cannot
read fails the whole import and names the line, never its contents.

### Moving from keep files

If this repository has a kept `.env` and no secrets of its own yet, `kunj secret list` says so and
prints the command that moves it:

```text
No secrets
Found a kept .env: kunj secret import ~/.kunj/shop-api/keep/.env --delete
```

`kunj setup` offers the same import. Nothing changes until you run it: keep files and `container.env`
keep working as before.

## Where secrets show up

**Commands on your machine.** `kunj run` starts a command with the branch's host secrets in its
environment, after writing their files into the worktree it runs in:

```bash
kunj run -- npm test
kunj run --branch fix/login -- $SHELL -l
```

It exits with the command's exit code. `kunj agent` and `kunj worktree shell` start their tmux
sessions under `kunj run`, so agents and the Workspace app's terminals get the same environment and
no value is ever on a command line; see [Agents in worktrees](../../worktrees/agent/#secrets).

**Worktrees.** `kunj worktree add` writes file deliveries into the new worktree, right after
[keep files](../../worktrees/keep-files/). `kunj secret apply` writes them into the worktree you are
in, and `kunj secret apply -a` into every worktree of the repository, each with its own branch's
secrets.

**Branch containers.** `kunj ct start` puts container-targeted environment secrets in the same
`docker run` environment as `container.env` (a stored secret wins over a `container.env` entry and
over the `gh auth token` fallback of the same name), and writes file deliveries into `/workspace`,
where they are added to `.git/info/exclude` so the agent cannot commit them. Docker fixes a container's
environment when it is created, so:

- a changed **file** secret reaches a container on the next `kunj ct start` (or a `kunj ct open` that
  has to start it);
- a changed **environment** secret needs `kunj ct start --rebuild`. `kunj ct start` reminds you, and
  `kunj ct list --json` shows `secretsChanged: true` for those containers.

`kunj ct agent` attaches to a running container and loads no secrets. Blueprint snapshots are built
without any. An environment secret cannot contain a newline (Docker's env file is line based);
deliver such a value as a file. `kunj ct token status` does not look in the store: it reports where
the token would come from without a stored `GH_TOKEN`.

<Aside type="caution">
Anything a container or command can read, its agent can read and send on. Give a secret the
`container` target only when the agent there should have it.
</Aside>

## Files that git does not ignore

kunj never writes a secret into something you could commit. A file delivery whose path git does not
ignore (or that is tracked) is refused with `not-ignored`, and nothing is written; add the file to
`.gitignore`, or pass `--force` to `kunj secret apply`. Paths outside the worktree, through a
symlinked directory, or inside `.git` are refused even with `--force`. `kunj run` and
`kunj worktree add` turn a refused file into a warning and carry on.

## Reading values back

```bash
kunj secret get DATABASE_URL               # one value, for scripts
eval "$(kunj secret env)"                  # export lines for your current shell
kunj secret env --target container         # what a container would get
```

`list` never shows values. `get` and `env` refuse `--json`, so values do not end up in the logs of
tools that record JSON output.

## The key

The store is encrypted with AES-256-GCM. The key is a random 32-byte key that kunj creates on first
use and keeps in the macOS Keychain (item `kunj-secrets`), or with `secret-tool` (libsecret) on Linux.
Without either, kunj asks for a passphrase once per command; three wrong tries give `secrets-locked`.
For CI and scripts, `KUNJ_SECRETS_KEY` (64 hex characters) supplies the key directly.

<SettingsTable category="secrets" />

Only commands that deliver or manage secrets open the store, and only when a `secrets.enc` exists.
Listings (`kunj worktree list`, `kunj ct list`, `kunj events`) never do, so they never prompt.

<Aside type="caution">
A copy of `~/.kunj/secrets.enc` is useless without its key: it cannot be opened without the
Keychain item, `KUNJ_SECRETS_KEY` or the passphrase, and losing the key loses the secrets. A damaged file is
reported as `secrets-corrupt` and left as it is; kunj never replaces it.
</Aside>

## Errors

With `--json`, errors carry a code: `secrets-locked` (no key, no terminal to prompt, or a wrong
passphrase), `secrets-corrupt`, `secret-not-found`, `bad-name` (names are letters, digits and `_`, not
starting with a digit), `not-ignored` and `bad-dotenv`.
